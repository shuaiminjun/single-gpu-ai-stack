# 一个真实的排障案例：把「闷 / 电音 / 杂音」变成数字

这个仓库的调度器解决的是"能不能跑"。而这个案例解决的是另一个更难的问题：**用户说"不好听"，你怎么知道改哪里、改完有没有变好。**

全部数字来自一台 AMD RX 7900 XT（20 GB，ROCm 7.2.1）上的真实链路：扒谱/分离 → 换音色 → 混音。

---

## 0. 起点：三条互相矛盾的反馈

> "伴奏跟捂着耳朵一样"、"唱歌声音差距大、一堆杂音"、"跟原版比更闷、更尖锐、缺细节"

主观描述互相矛盾（又闷又尖锐），直接调 EQ 一定会来回打转。所以先建度量。

| 指标 | 怎么算 | 用来判断 |
|---|---|---|
| 频谱质心 | `mean(librosa.feature.spectral_centroid)` | "闷"（偏低）/ "尖"（偏高） |
| 8–16 kHz 能量占比 | STFT 频带能量 / 总能量 | "缺细节" |
| 谱平坦度 | `spectral_flatness` 中位 | "杂音多"（越高越噪） |
| HNR | 自相关峰 / 总能量 | 谐波结构是否被破坏（"电音"） |
| F0 半音偏差 | `12·log2(f/f_ref)` 的逐帧中位 | 跑调 |
| 侧/中能量比 | `(L−R)/2` 与 `(L+R)/2` 的 RMS 比 | 有没有声场（是否为假立体声） |
| CAM++ 余弦相似度 | 说话人身份向量 | "这是谁的声音"（不是"听起来像"） |

---

## 1. 案例 A：「伴奏捂着耳朵」

**先证伪一个直觉**：是不是分离模型选错了？跑了 5 种 demucs 配置做 A/B（`htdemucs` / `htdemucs_ft` / `htdemucs_6s` × overlap / shifts）：

| 配置 | 8–16 kHz 保留率 | 质心偏移 |
|---|---|---|
| htdemucs ov=0.25 | 0.425 | −344 Hz |
| htdemucs ov=0.5 | 0.425 | −344 Hz |
| htdemucs_ft ov=0.5 | ≈0.42 | ≈−300 Hz |
| htdemucs_6s ov=0.5 | 0.423 | −270 Hz |

**结论：所有配置都只保留原曲约 42% 的高频能量。** 换模型没用——高频是在推理过程中被丢掉的，不是参数问题。

**修法**：频域能量再分配。原始混音的幅度谱里，8–16 kHz = 伴奏 + 原唱齿音；分离出的伴奏在这一带被压到约 0.4 倍，按 `|mix| / (|inst| + |vocal|)` 的比例把它放大回去（上限 2.0，防止放大噪声），并对人声齿音位置做掩蔽。

**但第一次修完更糟**：直接放大会把 AAC 编码噪声一起放大 —— 用户立刻反馈"杂音更多了"。于是加了噪声门（只补偿高于本底 2.5 倍的时频格）：

| | 8–16 kHz 保留率 | 质心 | 结果 |
|---|---|---|---|
| 修前 | 0.392 | 2898 Hz | 闷 |
| 无噪声门 | 0.543 | 3051 Hz | 亮但噪 |
| **加噪声门** | **0.515** | **3022 Hz** | 可用 |

原曲基准：质心 3091 Hz。

---

## 2. 案例 B：「没有立体声」

**根因**：源文件就是单声道（`soundfile.info().channels == 1`），整条链路又全在 mono 上做的。

**修法**：pseudo-stereo —— mid = 原信号，side = 320 Hz 高通后的 11 ms 延迟 + 55 ms 短混响，左右 = mid ± side。人声保持居中，宽度只作用于伴奏。

| | 声道 | 侧/中 | 左右相关 |
|---|---|---|---|
| 修前 | 1（或双单声道） | −61 dB | 1.000 |
| **修后** | 2 | **−15.4 dB** | **0.931** |

顺带修了一个 bug：LUFS 归一化原本是**每个声道分别**做的，会把整体推高约 3 dB（听感更冲），改成整轨归一。

## 3. 案例 C：「这声音是谁的？」

之前的判断全靠耳朵（"听着像"），这是不可接受的。用 CAM++ 做身份验证，并**先校准阈值**：

| 校准集（10 人 × 8 条，280 同人对 / 5441 异人对） | 余弦相似度 |
|---|---|
| 同人 mean / p05 | 0.740 / **0.557** |
| 异人 mean / p99 | 0.224 / **0.507** |
| EER | **1.71 % @ 0.48** |

有了阈值，判定就变成查表：

| 音频 | 与目标参考音的相似度 | 判定 |
|---|---|---|
| 微调模型 A 的输出 | 0.808 | 同人 ✅ |
| 音色转换链路 B 的输出 | −0.079 | **完全不是** ❌ |
| 另一个合成链路 C 的输出 | 0.163 | **不是** ❌ |

**这一步直接推翻了我之前"已经是目标音色"的结论** —— 客观指标救了后面的所有工作。

---

## 4. 这条链路上另外三个可复现的坑

| 现象 | 根因 | 数据 |
|---|---|---|
| 输出恒为 12.00 s 的循环垃圾 | 推理环境（GPU 路径/依赖版本）导致 LLM 不吐 EOS | 同权重在 CPU 环境 CER 0.000，GPU 环境 CER 1.0 |
| 给伴奏做 −3 dB @1.5–5 kHz 挖槽"让人声突出" | 直接把明亮度削掉 | 质心 2061 Hz（原曲 2696），用户："捂着耳朵" |
| `/free` 之后显存只回到 4/20 GB | 只卸模型缓存，不释放 HIP 上下文 | 必须杀进程重启，且要等 6–10 s 否则驱动 abort |

---

## 5. 结论

1. **主观反馈必须先翻译成指标**，否则"又闷又尖"会让你在两个方向之间反复横跳。
2. **A/B 要先证伪"参数问题"**——5 种配置都是 0.42，说明是系统性问题。
3. **修复本身会引入新问题**（放大高频 → 放大噪声），必须每步都测。
4. **身份类判断不能靠耳朵**，校准过的阈值才能下结论。

这套度量脚本在本仓库之外（它们依赖具体的语音模型），但方法可以直接搬。
